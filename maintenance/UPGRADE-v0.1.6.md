# 0.1.5 → 0.1.6 升级与应用回退

0.1.6 整合正式 0.1.5 的 WS 修复、已审查的上游候选和使用记录筛选。它是可人工安装的发行包，**不能从 0.1.5 直接通过现有托管控制器滚动升级**。控制器的同迁移集合检查保持不变；网页检查到新版本不代表它已获准自动安装。本发布没有更新任何生产环境。

## 唯一的结构差异

正式 0.1.5 源码为 `b3f8199dc3cc1e1520214fdd77832fc01b36578e`，迁移 fingerprint 为 `a6990935dd92d8132f2d487ba2b3320ac10d8819e72363db2d240bca23e4063f`。相对它仅新增：

- `343_usage_log_platform_snapshot.sql`：usage_logs 增加可空 VARCHAR(50) 平台字段及说明，无默认值、无历史回填，不修改金额或余额。
- `344_usage_log_platform_index_notx.sql`：非事务并发建立 `(platform, created_at DESC, id DESC)` 索引。已有的无效同名索引由迁移器在重试前并发删除重建。

旧 419 个迁移文件不变。fingerprint 按全部 SQL 文件真实内容生成，不能复制旧值、修改迁移账本或删除控制器保护来宣称兼容。

ADD COLUMN 仍需 ACCESS EXCLUSIVE 锁；长查询或事务会阻塞它。并发索引允许普通读写，但会扫描表、等待旧事务，并消耗 I/O、临时空间、WAL 和副本带宽。隔离小库通过不能证明大型生产表的执行时间或容量。没有经过业务规模评估的升级窗口，应继续保留稳定版。

## 维护窗口流程

1. 核实真实环境、运行二进制、主服务和全部 WS 网关、后台写入者、独立 sidecar、数据库与 Redis 的归属。保存旧二进制、镜像、资源、配置、加密密钥、控制器及代理状态；独立项目不在此升级范围。完成可恢复的备份与恢复演练，评估数据库及副本空间、长事务和索引大小。
2. 只从 SUB6 正式 Release 下载对应资产，校验 `checksums.txt`、GitHub digest/size、build-info 的 source_commit 与标签、BuildType=release 和真实版本。不要执行远端安装脚本。保持原有配置、密钥、资源、运行身份和图片桥接关闭设置。
3. 对入口进入维护状态，停止接受新请求与管理写入；排空 HTTP/SSE/WS、账务投递和所有后台写入者。随后停止旧主服务及网关，确认没有应用实例自动重启。此步骤有服务中断，不能宣称无感。独立项目及数据库服务不停止、不重建。
4. 使用目标环境的私有数据库参数运行新包的迁移模式。它只连接数据库，不启动 HTTP、Redis、后台任务或管理员初始化：

   ```sh
   ./sub6-linux-amd64 --migrate-only --migration-timeout=10m
   ```

   超时是上限示例，须按表规模确定。迁移器有可取消的 PostgreSQL advisory lock；执行超时／锁等待失败就保持维护状态，检查日志、长事务及索引状态后重试。不要为追求成功而无限延长等待或修改校验和。343 在事务中原子提交；344 可能留下无效索引，使用同一新版本迁移器重试修复。
5. 校验两项账本及 SQL checksum、平台列类型与 nullable、索引 indisvalid；核对旧账本保留、历史平台为 NULL、余额及账务投递／去重不变。重复执行迁移应跳过已完成项。若任一验证失败，不启动新业务实例。
6. 用新包在原配置和权限下启动主服务及全部网关；检查真实 `/proc/PID/exe` hash、版本、就绪、HTTP/SSE/WS、鉴权、支付回调及去重状态，再恢复流量。保留旧版与备份并观察账务、错误率、查询延迟、磁盘和副本延迟。大范围推理筛选读取原始记录，优先限定时间范围。
7. 托管部署需由运维依据已经验收的实际新容器、端点、二进制及真实 migration fingerprint 重建 `current` 记录并保留原私有历史；不得只改 fingerprint 绕过旧版升级门禁，也不要把旧 Compose 重新启动为 0.1.5。控制器协议和代码没有升级前置条件，因为本次跨迁移安装完全由运维完成。后续迁移集合相同的正式版本才能继续按现有控制器协议滚动升级。

## 回退边界

隔离验证覆盖：正式 0.1.5 的全部迁移集合升级、被锁时取消及重试、新旧列列表写入、旧版迁移读取器、旧账本和用量保留，以及升级前后的计费去重与金额一致。旧格式写入不包含 platform，新增列可空；旧进程忽略新平台快照。这里只证明这两项结构变更的兼容性，不承诺任意旧版本都能回退。

人工回退到正式 0.1.5 时，再次维护并排空全部新实例，替换应用二进制和对应资源／配置，保留已新增列、索引和完整迁移账本，验证新产生的用量和交易仍可读、去重仍生效，再恢复服务。**不执行 DROP COLUMN、DROP INDEX、删除新账本或整库还原**，避免丢失升级期间交易。旧控制器会因 fingerprint 不同拒绝跨集合回滚，这是预期保护；由运维执行应用回退并记录实际状态。旧版不显示平台及推理筛选新功能。

本流程需另一次明确生产升级授权。独立白名单 sidecar、其他域名项目和灾备容量处理分别安排。
