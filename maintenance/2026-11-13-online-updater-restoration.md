## 原因与修正

最初源码发行选择 BuildType=source。发布 0.1.1/0.1.2 二进制时继续沿用
这一参数，前端 VersionBadge 因此进入源码手动升级分支，隐藏原有“立即更新”
按钮。按钮和更新/重启 API 都仍在源码中，但正式交付没有恢复 release 模式。
这也导致在线回退入口进入源码提示，而非发行包操作。

发行归档里的程序名为 `sub6-linux-amd64`，旧更新器只解包 `sub2api` 或
`sub2api.exe`，因此仅显示按钮还不能完成升级。解包器现在识别 SUB6 的
稳定程序名和当前平台名，同时保留旧包兼容。不接受任意 `sub6-` 前缀文件。

根 Makefile 新增 build-release，先构建前端，再调用后端发行构建；
后端目标统一嵌入前端、版本/提交/日期和 BuildType=release，并使用只读模块。
Dockerfile 恢复 release 标记，验证 CI 改为调用相同发行构建目标。
默认开发构建仍是 source，保留源码安装者的原有行为。

## 审查边界

没有修改支付回调、签名、重放、订单所有权、金额/币种、入账、余额、计费、
用户鉴权或管理员路由。没有新增依赖、迁移、下载域名、远程执行脚本或插件。
更新仍需管理员操作，保留现有幂等和系统操作锁、待重启围栏、同目录原子替换
与二进制备份。没有添加自动调用升级/重启的后台任务。

更新/回退下载仍限定 `zhang2580384/SUB6` 的 HTTPS Release 路径，强制
checksums.txt；不切回上游二进制。解包保留路径穿越拒绝、普通文件和大小限制，
仅增加明确允许的文件名。CI 继续 contents:read 和固定 Actions 提交，
不发布资产、不连接生产、不授予新增权限。
